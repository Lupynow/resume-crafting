## 业务先行

**原则**：读者在理解你的技术选择之前，必须先知道你在做什么生意/什么系统。

判断标准：把技术名词全部遮住，剩下的话还能让人看懂这个项目是干什么的吗？

| 反面 | 正面 |
|---|---|
| 技术栈：Spring Boot + Redis + MQ + MySQL + Redisson | 校园二手交易平台，包含商品发布、订单交易、即时聊天和消息通知，本人负责商品和订单模块 |
| 使用 YOLOv8 做目标检测，mAP 提升 12% | 面向工地安全帽佩戴检测，在 4 路摄像头视频流上做实时推理，需在边缘设备 30fps 下运行 |

项目开头那一句背景不是套话，**它是后面所有技术决策成立的前提**。写"用了互斥重建避免缓存击穿"之前，得先说明这是个高频读的商品详情接口。

## 为什么 > 用了什么

这是最核心的一条。判断方法：**把这条读出来，问"换个技术行不行"**。

如果换成任何同类技术，这句话依然成立 → 你在说"我用过"。
如果换成别的技术就不成立 → 你在说"我知道为什么"。

| 只说了什么 | 说了为什么 |
|---|---|
| 使用 Redis 缓存商品信息，提高系统性能 | 商品详情属于高频读接口，缓存至 Redis；针对不存在的商品设置空值缓存避免穿透，热点 Key 失效时用互斥重建避免大量请求同时回源 |
| 使用 RabbitMQ 异步处理订单 | 订单创建后，将消息通知、积分累计等非核心操作通过 MQ 异步处理，减少主链路同步等待；消费端用业务唯一键保证幂等 |
| 用 RAG 实现知识库问答 | 纯向量检索在业务编号、专有名词等场景召回不稳定，因此增加 BM25 关键词检索，与向量结果通过 RRF 融合，再用 Rerank 重排 |
| 对 MySQL 建立索引 | 订单后台支持用户、状态、时间多条件查询，数据量上来后深分页变慢；按高频查询条件调整联合索引，大页查询改为游标分页 |

**注意最后一行**：从"建索引提速度"到"调整联合索引 + 改游标分页"，中间隔着一个**诊断过程**。面试官想听的就是这个过程。

### 怎么问出"为什么"

改简历时，对每条技术描述问用户：

1. 当时为什么选它？（试过别的吗？）
2. 不用它的话会出什么问题？
3. 有没有踩过坑？怎么解决的？

用户答不上来的，说明这条本来就不是他做的，或者他确实只是照着教程做的 —— 两种情况都不该按"我知道为什么"的方式写。

## 问题-方案-结果

三段式模板：

```
[业务场景/需求] → [遇到的问题] → [你的方案] → [量化结果]
```

完整度可以不同，但**至少有前两段**：

| 完整度 | 例子 |
|---|---|
| 只有动作（不合格） | 使用 Quartz 做定时任务 |
| 有场景 | 每日凌晨需汇总前一日订单报表，数据量约 80 万行 |
| 场景 + 方案 | …原同步查询会锁表影响线上，改为分页流式读取 + 中间表 |
| 场景 + 方案 + 结果 | …报表生成时间从 40 分钟降到 6 分钟 |

**没有结果就停在方案那一段**，不要编。

## 指标怎么选

### 优先选"能复现的"指标

| 指标类型 | 可信度 | 被追问时 |
|---|---|---|
| 数据集规模、文件数、条数 | 高 | 直接答 |
| 处理耗时、时间范围 | 高 | 直接答 |
| 准确率、命中率 | 中 | 需说清测试集怎么来的 |
| 性能提升百分比 | 低 | 需说清 baseline、压测工具、机器配置 |
| QPS 提升倍数 | 低 | 同上，且极易翻车 |

### 完整分布 > 满分数字

"命中率 100%"是危险信号 —— 面试官会立刻怀疑测试集是你自己出的、太简单。

改成给出分布：

> 自建 27 题检索基准：Top-1 命中 18/27、Top-5 命中 26/27、Top-20 全部命中，MRR 0.78。

这样写同时证明了三件事：**你做了评测、你懂评测指标、你不挑好看的数字报**。

配套的面试话术也要准备好，例如：

> 27 题里 Top-20 全中，但 Top-1 只有 66.7%。我专门看了没排第一的 9 道题，其中"能量密度双曲线如何表征设备健康"被排到第 11 位 —— 因为这题问的是概念，题干里没有文档中的原词。这说明当前系统对词面匹配依赖重，语义型查询的排序是短板，也是我给未来引入向量检索设的观察点。

**完整数据 + 归因 + 边界 + 下一步**，四样齐全。这比任何一个满分数字都有说服力。

## 动词的层级

同一个动作，不同的词暗示的参与深度差很多。**用词要匹配真实水位**：

| 动词 | 暗示 | 慎用场景 |
|---|---|---|
| 主导 / 独立完成 | 你定的方案、你写的 | 有他人在场时别用 |
| 设计 | 你出的方案 | 方案是别人给的别用 |
| 实现 / 搭建 | 你写的代码 | 只是调通了别用 |
| 参与 | 你在团队里 | 别整段都是"参与"，会显得没产出 |
| 协助 / 配合 | 你是配角 | 尽量少用，除非确实是 |
| 跟进 / 整理 | 事务性工作 | 技术岗简历里占比别太高 |

**全是"参与/协助/跟进"的简历等于在说"我在场，但不是我干的"。**

## 少写形容词，多写动作

形容词的问题是**每个人都写**。招聘方不会因为你写了「学习能力强」，就相信你学习能力强。

**判断方法**：把这句话拿去问"换个人的简历上是不是也能原样写？" 能 → 就是空话。

| 空话 | 改成 |
|---|---|
| 学习能力强 | 为准备运营岗位求职，整理 20 条同类岗位 JD，归纳 Excel、文案、数据整理等高频要求，并针对缺口补充学习 |
| 沟通能力好 | 在校园活动中负责参与人员通知、场地对接与现场协调，协助团队按计划完成活动 |
| 认真负责 | 负责 300 条报名信息的核对，发现并修正 17 条重复与缺失记录 |
| 抗压能力强 | 秋招期间同时推进 3 个方向的简历准备与投递，按各公司截止时间排序推进 |
| 有团队精神 | 与 4 人小组分工完成课程项目，负责数据清洗与结论验证，按期交付 |

**这三个词单独出现就删**：「认真负责」「学习能力强」「沟通能力好」。它们不是信息，是噪音。

**例外**：形容词后面**紧跟具体证据**时可以留 —— 「责任心强：连续 8 周跟踪同一批数据异常，直到定位到原因」。此时形容词的作用是**给证据起个标题**，而不是自己充当内容。

**同一原则适用于整份简历**：少写形容词，多写具体动作。读者相信动作，不相信自我评价。

## 技能栏的写法

技能栏是**索引**，不是**正文**。它的作用是让 HR 和面试官快速定位"这个人熟什么"，不需要展开解释。

反面：
```
- 熟悉 Java 基础，了解 JVM 内存模型、垃圾回收机制、类加载过程
- 掌握 Spring 全家桶，包括 Spring Boot、Spring Cloud、Spring MVC...
- 熟练使用 MySQL，了解索引优化、事务隔离级别、锁机制...
```
（这些应该放到项目经历里用具体场景体现）

正面：
```
- 语言与框架：Java、Spring Boot、MyBatis
- 数据存储：MySQL（索引优化、事务）、Redis（缓存设计、分布式锁）
- 中间件：RabbitMQ、Kafka
- 工程：Git、Linux、Docker、CI/CD
```

**每行一个类别，同类合并。** 3-5 行足够，占半页纸的技能栏是减分项。

## 不要给自己打分

| 不要写 | 改成 |
|---|---|
| Excel 掌握程度 90% | 能使用 Excel 完成筛选、排序、基础数据清洗和简单统计 |
| Python 熟练度 ★★★★☆ | 能用 Python 完成数据清洗、特征提取与可视化 |
| 英语水平：良好 | CET-6 580 分；能阅读英文技术文档 |
| Office 办公软件：精通 | 能使用 Word 排版长文档、用 Excel 做数据透视、用 PowerPoint 做汇报 |

**理由**：百分比和星级没有统一标准 —— 你的 90% 是别人的 60% 还是 100%？招聘方无从判断，只能当噪音忽略。

**描述你能做什么，而不是给自己打多少分。** 想表达"熟练"，就用**具体能完成的任务**来证明：不是"Excel 90%"，而是"能做数据透视表、VLOOKUP 跨表匹配和条件统计"。

**一个例外**：有客观凭证的可以写分数或等级（CET-6 580、雅思 7.0、软考中级）。因为那是第三方标准，不是自我评价。

## 该删的内容

按优先级（先删前面的）：

1. **和目标岗位无关的经历** —— 投技术岗时，"推进宣传册和易拉宝制作"占用两行是浪费
2. **罗列型条目** —— "沉淀 12 类问题拆解、95+ 决策矩阵、8 本 Cookbook、12 个 Playbook" 这种纯数字罗列，留一两个最有说服力的
3. **套话总结** —— "将个人经验型查找转为可复用、可评测、可追溯的知识工作流" 这类没有具体所指的句子
4. **自我评价栏** —— "学习能力强、抗压能力好" 删掉，没人信
5. **过细的技术细节** —— unpack 后逐条问："这条被问到，我能展开讲三分钟吗？" 不能就删

**删不是损失，是重新分配注意力。** 一页简历的空间有限，每删一条无关内容，就意味着硬货能多占一行。
