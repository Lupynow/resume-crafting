# resume-crafting

一个给 Claude Code（以及任何支持 Agent Skills 的客户端）用的**简历制作与审改 Skill**。

它的目标不是把简历写满，而是**让每一条都扛得住面试官往下追两层**。

---

## 为什么需要它

简历的问题几乎从不出在"没东西写"，而出在**写了但经不起追问**。

一个项目做了两三个月，Redis、MQ、MySQL、Spring Boot 都用过，最后简历上只剩：

> 使用 Redis 缓存热点数据，提高查询效率

这句话任何一个学过的人都能写。面试官看完不知道你遇到了什么问题、为什么这么设计、这东西是不是你真正做的。

**技术名词本身不值钱，值钱的是你为什么用、怎么做、踩过什么坑、最后效果怎么样。**

这个 Skill 把"怎么写才算扛得住追问"变成了一套可执行的流程。

---

## 两条路径

| 情况 | 走哪条 |
|---|---|
| 手里没有简历，或只有一个粗糙初稿 | **路径 A：从 0 到 1** |
| 有一份成型简历，想改好 | **路径 B：审改** |

### 路径 A：从 0 到 1

先收素材（周报、项目文档、旧简历），建出事实底稿，再针对缺口逐条追问——**追问要到能扛住面试的深度**，不满足于"我做了数据清洗"，而是"缺失值怎么处理、为什么这么处理、结果是什么"。

答不上来的细节就不写进简历，这是正常取舍。

### 路径 B：审改

先诊断再动手。把每条经历分类：

| 类型 | 特征 | 处理 |
|---|---|---|
| 能扛两轮追问 | 有具体数字、有取舍理由 | 保留，微调表达 |
| 只能扛一轮 | 有动作，缺"为什么" | 补设计理由 |
| 一问就崩 | 全是名词、罗列、套话 | 删除或重写 |

---

## 核心：真实性审计

**这是整个流程里最不能省的一步。**

写简历的人会不自觉地把三样东西混在一起：

1. **方案里设计的** —— 文档里写得清清楚楚，但代码没实现
2. **实现了但没生效的** —— 代码写了，数据或配置没到位
3. **真正跑通的** —— 有代码、有运行、有输出

这三样在纸上看起来一模一样。Skill 会逐条核验，把每条表述**降到"能扛住代码核验"的水位**：

| 不能写 | 应该写 |
|---|---|
| 实现自动查询重写（≤3 轮） | 由 Agent 继续检查信息缺口 |
| 4 万 Token 硬限制 | 最多组装 30 个片段、60000 字符的证据包 |
| 支持页码、幻灯片、章节、时间四类定位 | 结果保留页码、章节或幻灯片定位 |
| 审核状态显著提升排序质量 | 实现审核状态排序（代码里有，当前数据未触发） |

**降级不是损失。** 知道自己的边界在哪，本身就是能力——而且"逻辑实现了但数据未到位"这种回答，比硬撑强得多。

---

## 交付物

除了改好的简历，还会产出：

- **修改说明** —— 改了什么、为什么，可对照原件
- **追问预演** —— 针对你自己写的每一条，预测面试官会怎么深挖
- **面试题** —— 目标岗位的通用题库（与追问预演分开）
- **跨版本数字核对** —— 多份简历同一指标必须一致

## 用法

直接说就行：

```
帮我看看我的简历，投了三个月没什么回音
我要投 XX 公司的后端实习，简历要怎么改？
我大三还没写过简历，能帮我从零做一份吗
我简历上写了用 Redis，但其实我没做过，怎么办
```

Skill 会自动判断走哪条路径。

## 几个实战踩出来的坑

这个 Skill 经过两轮对照测试（带 skill vs 不带），测试过程中发现并修复了五个真实问题。这些坑写进了 Skill，也是它存在的意义之一：

**1. 检查工具本身可能是瞎的**

最初用 `pandoc` 提取简历文本做残留检查。但 **pandoc 会把超链接字段整个丢掉**——而邮箱和 GitHub 链接恰恰都在超链接里。结果：一份还残留 `your@email.com` 的简历，检查脚本报"clean"。

现在直接读 OOXML，取 `<w:t>` + `<w:instrText>`。

**2. 文档属性会泄露上一任模板作者**

从别人（或自己以前的版本）的模板起稿时，`docProps/core.xml` 里的作者、标题、关键词会**原样继承**。正文全部改好、占位符也换干净了，HR 点一下"文件属性"就能看到：

```
作者：某某某
标题：某某某 - XX岗位简历
关键词：XX岗位, XX技能
```

**3. 样式断链会静默降级**

`<w:pStyle w:val="167">` 里的值必须和 `styles.xml` 里的 `w:styleId` 一字不差。一旦对不上（比如把数字 ID "顺手规范化"成样式名），Word **不报错**，静默回退默认样式——文件能打开、页数也对、看着像份简历，但配色字号全丢，交付的是张白板。

**4. 宁给完整分布，不给满分数字**

```
❌ 检索命中率 100%
✅ Top-1 命中 18/27、Top-5 命中 26/27、Top-20 全部命中，MRR 0.78
```

后者同时证明了你会评测、懂指标、不挑好看的数字报。前者只会招来"基准集怎么建的""有没有负样本"的追问。

**5. 页脚方向躲过了所有「正文检查」**

定向版简历的头部和页脚**各印一份目标方向**。改方向时只改头部、漏改页脚，就得到一份自相矛盾的文件：

```
头部：张三  产品运营 / 数据分析（2027届）
页脚：张三 | 竞品研究 / 数据分析 | 第 1 页
```

页脚是独立的 XML 部件（`word/footer1.xml`），**任何基于正文文本的检查都不会覆盖它**；而且两个方向标签各自看着都「合理」，不并排对比根本发现不了。

这不是靠"再仔细一点"能避免的——它是结构性的疏漏。现在 `check_residue.py` 会自动比对头部与页脚的方向标签。

## 环境说明

主要在 Windows + Word/WPS 环境下开发和验证：

- 页数统计走 COM 接口（纯 Python 库无法准确还原 Word 的分页）
- 所有文件操作显式 `encoding='utf-8'`
- 脚本不依赖特定路径，开箱即用

其他平台可以换用 LibreOffice 做页数校验，`check_residue.py` 和 `render_pdf.py` 是跨平台的。
